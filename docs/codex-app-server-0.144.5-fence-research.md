# Codex app-server 0.144.5 fixture and MCP-fence research

Scope: official `@openai/codex` 0.144.5 evidence only. The reviewed surface is the published npm
target, the schema generated by that exact binary, and OpenAI's `rust-v0.144.5` source tag. This
record does not treat Zylos protocol injection, a fake/model-loopback provider, `codex exec`, a
second transport, or repeated remote-model prompts as official-target evidence.

> Product disposition update (2026-07-23): the user explicitly revised the migration consensus to
> allow all effectively enabled MCP services to execute automatically without Core approval. The
> source findings below remain accurate historical security evidence, but their earlier
> "MCP remains fail-closed" product disposition is superseded. The accepted implementation risk is
> that MCP access is not proven to obey workspace leases, provider sandboxing, or protected-action
> approval. Unknown outcomes still must not be replayed automatically.

## Conclusions

| Acceptance question | Official 0.144.5 conclusion |
|---|---|
| Deterministically force command approval over `app-server --stdio` | **No supported runtime trigger found.** The official test client's command named `trigger-cmd-approval` only submits a natural-language prompt to the model. |
| Deterministically force file approval | **No supported runtime trigger found.** `trigger-patch-approval` is also only a prompt. |
| Deterministically force `item/tool/requestUserInput` | **No supported runtime trigger found.** The test client can answer the request after the server emits it, but has no command or RPC that makes the server emit it. |
| Forge stale server notification/request/response traffic | **No supported runtime trigger found.** The generated client-request surface has no emit/forge/stale/fixture method. |
| Test-only protocol artifacts | `mock/experimentalMethod`, `thread/start.mockExperimentalField`, schema fixtures, and in-repository mock/loopback tests exist, but none emits any target server request or stale traffic. The mock method only echoes one value; the mock thread field is ignored by the handler. |
| Model-initiated MCP pre-action fence | **A conditional synchronous seam exists.** With per-server/tool approval mode `prompt`, `approvalPolicy=on-request`, user review, no auto-allowing hook/Guardian/cache, and `tool_call_mcp_elicitation` enabled, app-server waits for `mcpServer/elicitation/request` to be answered before it calls the MCP tool. Core can check its lease before returning one-shot `accept`. |
| Client-initiated `mcpServer/tool/call` | **Not fenced by that seam.** It dispatches directly to `thread.call_mcp_tool` / `manager.call_tool`. Zylos must keep this RPC unreachable; it cannot be used as positive Global14 evidence. |

Therefore the fixture blocker remains for command approval, file approval, `requestUserInput`,
stale traffic, and a deterministic model-initiated MCP call. However, the older broad claim that
0.144.5 has no MCP pre-action capability is incorrect. The official source contains a usable
candidate seam for model-initiated MCP calls, subject to the fail-closed conditions below. That
source finding is not itself a Global14 PASS: the configuration, bypass prevention, durable Core
interaction, one-shot answer, provider acknowledgement, terminal state, and restart behavior still
need implementation and real evidence.

## Why the apparent official fixtures do not unblock real acceptance

### Approval commands are prompts, not fixtures

The official
[`app-server-test-client`](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/app-server-test-client/src/lib.rs#L962-L1011)
implements `trigger_cmd_approval` by sending a natural-language request that asks the model to run
a bounded command, and implements `trigger_patch_approval` with another natural-language tool-use
request. Both set approval and sandbox policy, but neither
injects a tool call or server request. Their result still depends on model behavior, matching the
already observed `triggered=false` runs.

The same test client
[`README`](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/app-server-test-client/README.md#L21-L31)
says `send-message` and `send-message-v2` *handle* `request_user_input` interactively. Handling a
request after it appears is not a trigger. The client has no `trigger-request-user-input` command.
Its documented loopback Responses API server is a mock provider used for plugin analytics, which is
outside this acceptance boundary.

### `mock/experimentalMethod` and the mock thread field are inert

The protocol source labels
[`mock/experimentalMethod`](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/app-server-protocol/src/protocol/common.rs#L938-L944)
as a test-only experimental-gating method. Its
[`catalog_processor`](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/app-server/src/request_processors/catalog_processor.rs#L479-L485)
implementation only returns `{ echoed: value }`. Likewise,
[`thread/start.mockExperimentalField`](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/app-server-protocol/src/protocol/v2/thread.rs#L138-L164)
is a schema-gating field, and `thread_start_inner` destructures it into an unused
`_mock_experimental_field`. Neither can emit approval, input, MCP, or stale traffic.

The source-tree `schema_fixtures` are generated type/schema golden files, not a running-server
fixture. OpenAI's maintainer instructions explicitly call regeneration of protocol fixtures after
changing experimental fields; they do not describe a server behavior driver. See the official
[`README`](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/app-server/README.md#L2179-L2229).

### `thread/inject_items` only records model-visible history

The public README describes `thread/inject_items` as appending raw Responses API items to history
without starting a turn. The handler deserializes and validates items, then calls
`inject_response_items`; Core records them with `inject_no_new_turn` and flushes the rollout. It
does not execute the item or emit its server-request lifecycle. See
[`turn_processor.rs`](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/app-server/src/request_processors/turn_processor.rs#L802-L827)
and
[`codex_thread.rs`](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/core/src/codex_thread.rs#L468-L494).
At most it changes a later model prompt, which remains nondeterministic.

### No supported stale-traffic driver

The generated experimental request union is the authoritative version-specific client surface.
It has no request that tells app-server to replay an old connection/request ID or emit a forged
notification/request/response. OpenAI's transport and processor tests can construct private
`OutgoingMessage` values in-process, but those Rust test helpers are not an app-server RPC, CLI
option, or packaged target capability. They cannot count as real official-target traffic.

## Conditional MCP pre-action seam

### Official ordering

For a **model-initiated** MCP tool call, the 0.144.5 source orders the path as follows:

1. `handle_mcp_tool_call` emits the provider item-start event, then awaits
   `maybe_request_mcp_tool_approval`; it does not call the MCP server yet. See
   [`mcp_tool_call.rs` lines 227-317](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/core/src/mcp_tool_call.rs#L227-L317).
2. Approval mode `Prompt` requires approval for every tool, independent of MCP annotation. See
   [`requires_mcp_tool_approval_for_mode`](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/core/src/mcp_tool_call.rs#L2163-L2193).
3. `tool_call_mcp_elicitation` is stable and enabled by default. With that feature enabled, the
   approval function calls `request_mcp_server_elicitation(...)` and **awaits** its response. See
   [`features/src/lib.rs` lines 1263-1268](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/features/src/lib.rs#L1263-L1268)
   and
   [`mcp_tool_call.rs` lines 1203-1360](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/core/src/mcp_tool_call.rs#L1203-L1360).
4. App-server maps that event to the bidirectional
   `mcpServer/elicitation/request`, waits for the client result, then submits
   `ResolveElicitation`. See
   [`bespoke_event_handling.rs` lines 763-783 and 1650-1675](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/app-server/src/bespoke_event_handling.rs#L763-L783).
5. Only an accepted decision enters `handle_approved_mcp_tool_call`; the external call occurs later
   at `manager.call_tool(...)`. See
   [`mcp_tool_call.rs` lines 362-408 and 566-599](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/core/src/mcp_tool_call.rs#L362-L408).

This is a real synchronous pre-action boundary: a client can hold the server request while Core
reopens and validates its durable lease facts, then send one-shot `accept` only if they are current.
An `item/started` notification precedes the boundary, but the MCP external call does not.

### Conditions that must be proved before claiming Global14

The seam is conditional, not a first-class unconditional lease hook. A conforming implementation
must prove all of the following:

- Every enabled MCP server uses `default_tools_approval_mode="prompt"`, and no per-tool
  `approval_mode="approve"` overrides it. `Prompt` and the per-tool precedence are defined in
  [`config/src/mcp_types.rs`](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/config/src/mcp_types.rs#L19-L27)
  and `mcp_tool_call.rs` lines 1034-1062. `Prompt` also disables remembered approval keys
  (`session_mcp_tool_approval_key` returns `None` unless mode is `Auto`) and normalizes any
  session/persistent choice back to one-shot `Accept`; see `mcp_tool_call.rs` lines 1397-1424 and
  1925-1940.
- `approvalPolicy` remains `on-request`. The official
  [`mcp_permission_prompt_is_auto_approved`](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/codex-mcp/src/mcp/mod.rs#L77-L97)
  does not auto-approve `OnRequest`, but it does bypass prompts for approval mode `Approve` and for
  some `Never`/unrestricted combinations.
- Review routes to the app-server client, not Guardian, and permission hooks cannot return `Allow`
  before the client request. The hook and Guardian early-return paths are visible at
  `mcp_tool_call.rs` lines 1242-1292.
- The app-server client identity must not activate the Xcode 26.4 compatibility path. Official
  `xcode_26_4_mcp_elicitations_auto_deny` is limited to `client_name == "Xcode"` with a `26.4...`
  version (`thread_processor.rs` lines 3879-3888); a Zylos identity must be asserted so the real
  client request is emitted.
- Core returns only the current one-shot acceptance after its durable lease check. `Prompt` mode
  removes the official remembered-approval key path, but this still needs a protocol assertion in
  the adapter tests.
- The thread's generic `config` override must authoritatively pin the MCP server table, approval
  modes, reviewer, and feature state rather than accidentally merging a permissive provider-local
  override. `ThreadStartParams.config` is accepted at
  [`protocol/v2/thread.rs` lines 80-95](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/app-server-protocol/src/protocol/v2/thread.rs#L80-L95)
  and loaded by `thread_start_task` at `thread_processor.rs` lines 1090-1109, but the exact
  fail-closed override proof belongs in implementation tests.
- The same connection/thread/turn/request/attempt/lease and durable handoff fencing used for other
  server requests must cover the MCP elicitation and its `serverRequest/resolved` acknowledgement.
- Any direct or alternative MCP execution surface remains unreachable.

### Direct `mcpServer/tool/call` is a bypass, not evidence

The official client request
[`mcpServer/tool/call`](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/app-server/README.md#L233-L238)
does not enter the model-initiated approval path. The processor immediately spawns
`thread.call_mcp_tool`, which directly invokes `manager.call_tool`. See
[`mcp_processor.rs` lines 455-474](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/app-server/src/request_processors/mcp_processor.rs#L455-L474)
and
[`codex_thread.rs` lines 647-658](https://github.com/openai/codex/blob/rust-v0.144.5/codex-rs/core/src/codex_thread.rs#L647-L658).
It must stay outside Zylos's private sender allowlist. A deterministic test that calls this RPC
would prove only that an unfenced side-effect surface exists; it cannot satisfy Global14.

Ordinary MCP-server-originated elicitations also do not, by themselves, prove a pre-action fence:
the public protocol says an MCP server can interrupt a turn and ask the client for input, but does
not guarantee that the server made no earlier external side effect. The relevant pre-action seam is
Codex's **tool-approval** elicitation before `manager.call_tool`, not arbitrary downstream
elicitation.

## Session disposition

- No additional prompt-based command, file, `requestUserInput`, or MCP attempt was made after the
  fixture search established that the official target has no deterministic trigger.
- At the time of this research MCP remained fail-closed. That historical disposition was superseded
  by the explicit 2026-07-23 product authorization; it is not retroactively a Global14 security PASS.
- No consensus, issue acceptance, external service, container, image, or persistent volume was
  changed or removed. This report is the only repository change from this session.

## Closure paths for the remaining real-fixture blocker

1. **Upstream official fixture/capability.** Obtain an OpenAI-supported, stdio-compatible fixture
   or protocol mode for the published target that deterministically emits command approval, file
   approval, `requestUserInput`, model-initiated MCP tool approval, and named stale traffic without
   a fake provider or external side effect. For MCP hardening, the upstream request should also ask
   for an explicit per-thread fail-closed “client must approve every MCP tool call” contract and an
   option to gate or disable direct `mcpServer/tool/call`.
2. **Issue-owner acceptance decision.** The owner explicitly changes issue acceptance to accept the
   existing deterministic injected-protocol matrices plus the real official-target
   attempted-but-not-triggered evidence. The record must continue to say these are not real positive
   server-request passes. The subsequent 2026-07-23 requirements revision separately authorized
   automatic MCP execution while accepting the missing pre-action isolation proof; this research
   itself did not provide that authorization.
